# Working notes — omarchy-plymouth-nier

Context for anyone (human or agent) changing this theme. The screen it draws
**cannot be previewed from a running session**, so almost everything here is a
trap that was only found by disassembling Plymouth or by rebooting into a
broken screen. Read this before editing.

## What this is

A Plymouth theme with two faces, selected by `Plymouth.GetMode()`:

- **boot** — the LUKS passphrase prompt. Ghost word, ambient katakana field,
  vertical column, HUD brackets, welcome line, segmented password rule, typed
  marks, rejection handling, post-unlock progress line.
- **shutdown / reboot** — a farewell screen only: brackets, "Goodbye, <name>",
  a rule, "SYSTEM OFFLINE". The ambient field is never built, not merely
  hidden, and the progress line never appears.

Everything is generated by `build-theme.py`, which emits 206 files: the PNG
assets, `omarchy.script`, and `omarchy-minimal.plymouth`. There is no
hand-edited copy of the script — edit the generator.

## The target is Plymouth, not SDDM

Omarchy autologins (`/etc/sddm.conf.d/autologin.conf` sets `User=` and
`Session=`), so the SDDM greeter is essentially never seen. The screen at
power-on is the Plymouth splash driven by the `encrypt` mkinitcpio hook. A
whole round of work went into the wrong screen before this was noticed.

On a Unified Kernel Image setup (Limine, `/boot/EFI/Linux/omarchy_linux.efi`)
there is no separate `initramfs-*.img`; kernel, initramfs and cmdline are
bundled in that one `.efi`, and `mkinitcpio -P` is wrapped to also run
`limine-mkinitcpio`.

## Five traps

**1. `Image.Scale` is nearest-neighbour.** `ply_pixel_buffer_resize` contains
two `mulsd` (the x/y step ratios) and no per-pixel blending whatsoever. Any
antialiased image it touches is destroyed. Assets are therefore rendered at
their exact final pixel size, and only flat-colour tiles get scaled at
runtime, where that sampling is lossless.

**2. Plymouth picks device scale 2 on HiDPI.** `ply_guess_device_scale`
computes `DPI = width*254/(10*(width_mm+1))` and takes the low-DPI branch only
at or below 96. A 2880x1800 panel of 310x200 mm is 235 DPI, so without
`DeviceScale=1` in `/etc/plymouth/plymouthd.conf` the theme gets a 1440x900
logical window and every image is doubled with the sampler above. plymouthd
reads no `conf.d`, and that file belongs to the `plymouth` package (it is in
its backup array, so edits survive upgrades and produce a `.pacnew`), which is
why the install scriptlet edits it in place instead of shipping it.

Do not verify this by reading `/sys/class/graphics/fb0/virtual_size` after
boot — that says nothing about the logical window Plymouth hands the theme.

**3. Scoping.** In this scripting language:

| case | result |
|------|--------|
| the name already exists as a global | an in-function assignment **writes through to the global** |
| the name is not a global | stays local to the call; nesting two functions using it is safe |
| function **parameters** | always local, and they shadow a global of the same name |

This made the entire ambient field invisible once glyph creation moved into a
helper: the helper wrote to `amb.sprite[i]` and `amb` had never been assigned
at top level, so every sprite was discarded on return. All such arrays are now
pre-declared at top level. The helpers also use unique loop counters
(`ti`, `pi`, `di`, `si`, `tb`) so a future edit cannot reintroduce the clash.

**4. There is no "wrong password" event.** plymouthd has a single
`update_display()` that picks display_password / display_question /
display_normal from its pending entry-request queue, and
`plymouth ask-for-password --command=...` — what the `encrypt` hook runs —
re-issues the request itself when the command exits non-zero. So:

- correct key: `display_password` → Enter → `display_normal`, and nothing more
- wrong key: `display_password` → Enter → `display_normal` → `display_password`

The theme cannot decide at Enter time. It enters a verifying state and
resolves later, and treating that `display_normal` as an unlock (which earlier
versions did) makes a wrong passphrase fade the whole screen out and start the
progress bar before snapping back.

**5. What *does* signal acceptance: the progress pause.**
`plymouth ask-for-password` pauses boot progress while it asks — that is what
its `--dont-pause-progress` flag disables, and the `encrypt` hook does not
pass it. While paused, `ply_progress` freezes both the percentage and the
elapsed time, yet `ply_boot_splash_update_progress` re-arms its 33 ms timer
unconditionally, so the theme keeps being called with frozen values.

Progress standing still **is** the key being checked. Progress moving again
**is** `ask-for-password` having finished, i.e. the key accepted.

Two earlier attempts at this both failed, for instructive reasons:

- *Counting frames.* The script refresh is a timer re-armed **before** the
  script runs, so its real rate is at best `1/(0.02 + script_time)` — and
  during the check argon2 saturates the CPU, starving exactly the thing being
  counted. The commit never arrived.
- *Reading `ply_progress_get_time`.* A genuine wall clock (it is the **first**
  argument of the boot-progress callback; `ply_progress_get_percentage` goes
  into xmm1 and is the second), but it is frozen by the very pause it was
  meant to time.

`frozen_needed` requires ~0.5 s of proven freeze before the resume is trusted,
so a system that never pauses progress does not commit instantly;
`resume_secs` requires 0.35 s of real movement so a momentary unpause cannot
false-trigger. A 17 s wall-clock fallback and a frame-counted backstop remain
for systems that behave differently. For reference, this header is argon2id
with 9 iterations over 1 GiB and takes **15.8 s** to reject a key — measured
with `cryptsetup open --test-passphrase`, not guessed.

## Two things that are not possible

- **A clock.** `strings` on `script.so` lists every function the language
  exposes and there is no time or date call anywhere. The greeting is static
  because of this, not by preference.
- **Tinting a sprite.** Colour transitions are crossfades between two stacked
  sprites of identical size that differ only in fill — see
  `denied_rust.png` / `denied_bone.png`.

Also absent: `Math.Exp` (decay is `(1-u)^3`), video, shaders. Present and used:
`Math.Random/Sin/Cos/Sqrt/Int`, `String.CharAt/SubString/Length`, and
`Image.Text(text, r, g, b, a, font, align)`.

## NEVER run plymouthd from a session

An attempt to preview the theme live by starting `plymouthd` with the `x11`
renderer (it exists, and `DISPLAY` is set under XWayland) took over the
console: a log-spewing screen, no working keyboard, and an unresponsive power
button. plymouthd grabs the console regardless of which renderer it ends up
using. Nothing persists — `/run/plymouth` is recreated empty at boot — but
there is no safe way to do this. Use the harnesses below.

## Verification routine

Run all of it before every `mkinitcpio -P`:

1. `python3 build-theme.py /tmp/out` — assets and script
2. `gcc -o /tmp/plyparse tools/plyparse.c -ldl && /tmp/plyparse /tmp/out/omarchy.script`
   — Plymouth's own parser, via `script_parse_file`. Keep a deliberately
   broken script around as a negative control.
3. `gcc -o /tmp/plyrun tools/plyrun.c -ldl` — actually executes the script.
   It registers only the math and string libs, so the script under test
   supplies its own stubs (`tools/prelude.script`), then C reads named globals
   back. `script_state_t` is `{ user_data, global, local, this }`: the global
   hash is at **offset 0x8**, not 0.

   ```bash
   sed 's/@MODE@/boot/' tools/prelude.script > /tmp/pre.script
   cat /tmp/pre.script /tmp/out/omarchy.script tools/verify.script > /tmp/t.script
   /tmp/plyrun /tmp/t.script amb_alive seg_bone_alive shard_alive ui_final
   ```

   `tools/verify.script` covers the rejected-key visuals, `verify-clock.script`
   the paused-progress detection. Run `@MODE@` as `boot`, `shutdown` and
   `reboot`.
4. Install, `plymouth-set-default-theme omarchy-minimal`, `mkinitcpio -P`.
5. **Re-run 2 and 3 against the script unpacked from the built image**, never
   the copy in `/usr/share`:

   ```bash
   objcopy -O binary --only-section=.initrd \
       /boot/EFI/Linux/omarchy_linux.efi initrd.img
   lsinitcpio -x initrd.img
   ```

Harness loop counters must be odd names — `qq`, `zz`, `qi`, `nn`. A test loop
using `i` or `b` is clobbered mid-iteration by `refresh_callback`, per trap 3.
That produced an infinite loop once.

`tools/preview-arranque.html` and `preview-apagado.html` are canvas
simulations used to agree on a design before baking it into the boot image.
They carry the same `SCALE` as the generator; keep them in sync.

## Rebuilding the boot image is not always `mkinitcpio -P`

On a Limine + UKI system there are no mkinitcpio presets at all:
`/etc/mkinitcpio.d` is empty and `mkinitcpio -P` fails with "No presets
found". The `mkinitcpio` on PATH there is an interactive wrapper from
`limine-mkinitcpio-hook` that prompts before doing anything, and a pacman
scriptlet's PATH excludes `/usr/local/bin`, so it silently reaches the real
binary and fails. The install scriptlet therefore prefers
`/usr/bin/limine-mkinitcpio`, falls back to `/usr/bin/mkinitcpio -P` when
presets exist, and warns loudly if neither applies rather than pretending it
worked.

## Rollback

```bash
sudo plymouth-set-default-theme omarchy && sudo mkinitcpio -P
```

The stock theme at `/usr/share/plymouth/themes/omarchy/` is never modified.
`pacman -R omarchy-plymouth-nier` does this automatically. Plymouth script
failures normally fall back to a plain-text `systemd-ask-password` prompt
rather than blocking boot, so a bad theme is recoverable without rescue media.

## Suspend does not retrigger it

The disk stays decrypted across suspend; only a real power-off and boot runs
the LUKS prompt again. There is no shortcut for testing this screen.
